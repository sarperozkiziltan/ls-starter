# Scene Setup Playbook (Lens Studio)

> **Status:** v0.1 — living document. This is the accumulated, hard-won knowledge of how
> *this user* builds Lens Studio scenes. It is written by Claude, corrected by the user,
> and it grows after every session. Read it fully before touching a scene.
>
> **Maintenance rule:** every time the user corrects a placement, a naming choice, a
> component setup, or a workflow step — write the lesson into this file **in the same turn**,
> phrased as a rule, not as a story. Never delete a rule without the user saying so.
> Never write learnings into `AGENTS.md` — that file is auto-generated by Lens Studio
> and will be overwritten.

---

## 0. Prime Directives

1. **The storyboard is the spec.** The user supplies a storyboard image. Every element's
   position, size, and layer order comes from it. Do not invent layout.
2. **Look before you place.** Introspect the existing scene graph (`scene-graphql`) and the
   camera/screen setup *before* creating anything. Never assume an empty scene.
3. **Verify visually, every step.** After each meaningful change, capture the Preview
   (`CaptureRuntimeViewTool` / `PreviewPanelTool`) and compare against the storyboard.
   A change is not "done" until it has been seen.
4. **Build incrementally.** One element (or one coherent group) at a time. Confirm it renders
   correctly before moving to the next. Do not batch-create a whole scene blind.
5. **MCP only.** All Lens Studio interaction goes through the `mcp__lens-studio__*` tools.
   Never `curl`/`fetch` the MCP server. If a tool fails, stop and report.
6. **Report honestly.** If something did not land where intended, say so and show the capture.

## 1. Where the Storyboard Lives

Storyboards are kept in the repo at `Docs/Storyboard/`, named for what they contain and
nothing else — `Storyboard.png`, `Score Result Logic.png`. No date, no version suffix, no
export timestamp; strip whatever the export tool appended.

- **Never** put reference images under `Assets/` — Lens Studio scans that directory and imports
  any image there as a texture, polluting the asset library.
- Screenshots pasted into chat live in a macOS temp folder that gets deleted; copy them into
  `Docs/Storyboard/` immediately so they survive the session.
- **At the start of any scene work, read every file in `Docs/Storyboard/`.** The folder is small
  and each file covers a different part of the spec — layout, scoring, copy — so there is no
  "newest one" to pick.
- **A revision overwrites the file it replaces.** Git history keeps the old version; a folder of
  `-v1`, `-v2`, `-v3` only creates the question of which one is current.

## 2. Standard Workflow

```
storyboard received
  └─ 1. Read the storyboard: list every element, its screen region, its z-order
  └─ 2. Introspect current scene (hierarchy, cameras, screen regions, existing assets)
  └─ 3. Confirm the plan / anchor mapping with the user if ambiguous
  └─ 4. Build ONE element
  └─ 5. Capture preview → compare to storyboard → self-critique
  └─ 6. User feedback → fix → WRITE THE LESSON INTO THIS FILE
  └─ 7. Next element (back to 4)
```

### Before creating anything, always answer these five:
1. **Parent** — `Global`, `Selfie`, or `World`? Diff the storyboard's world frame against its
   selfie frames; do not fall back to `Global`.
2. **Layer** — `2D UI` (survives capture) or `Hint Camera` (live preview only)?
3. **Scale** — `±texture_width / 720`, computed, never estimated.
4. **Vertical** — which screen edge is it pinned to, and what drives the opposite edge?
5. **Render order** — who does it sit above and below on its layer?
6. **Which storyboard frame does it belong to?** Tell the user, so they can set its Fader's
   `initialState`. Leave the object enabled either way.

Answer all five *before* the first mutation. Skipping one produces an element that looks right
in the preview and is wrong somewhere invisible — the wrong camera facing, missing from captures,
or drifting on another aspect ratio.

## 3. Scene Conventions

### Where 2D UI goes — the Global / Selfie / World split

**Every screen-space image and text goes under the `2D  UI` camera** (note the double space in
the name), never under `Camera 3D`. The template ships this hierarchy:

```
2D  UI                              [Camera, orthographic]
└─ Full Frame Region - Global       [ScreenTransform + ScreenRegionComponent = FullFrame]
   ├─ Global    ← visible in BOTH selfie (front) and world (rear) camera
   ├─ Selfie    ← visible ONLY on the front camera
   └─ World     ← visible ONLY on the rear camera
```

**There is no default — read it off the storyboard.** The storyboard has a world-view frame
alongside the selfie frames; **diff them**. An element drawn in both is `Global`; an element
drawn only in the selfie frames is `Selfie`; one drawn only in the world frame is `World`.

Worked example from an earlier project's storyboard:

| Element | Selfie frames | World frame | → Parent |
|---|---|---|---|
| TD-Bank_Logo | ✓ | ✓ | `Global` |
| Rank-Your-Investments_Titile | ✓ | — | `Selfie` |
| Hint-FlipCamera | — | ✓ | `World` |

Getting this wrong is invisible in a front-camera preview and only surfaces after a camera flip,
so resolve it from the frames **before** creating the object — reparenting afterwards preserves
anchors and layer, but the check is cheap and the miss is silent.

### Layer and render order — decide both for EVERY screen image

Two separate questions, asked every single time an image is created. Neither has a safe default
you can skip.

#### 1. Which layer?

| Layer | Mask | Camera → Render Target | Appears in a captured Snap? | Put here |
|---|---|---|---|---|
| **2D UI** | `4` | `2D  UI` → Main RT | **Yes** | Logo, titles, ranking system, anything that must survive into the saved/shared Snap |
| **Hint Camera** | `2` | `Live Camera` → Live RT | **No — live preview only** | Hints and CTAs: "Flip Camera", "Bring this to the booth", replay/UI affordances |

The distinction is *post-capture visibility*, and the test is one question: **should this still
be there in the Snap the user saves and sends?**

- A hint or affordance — "Flip Camera", a replay button — is noise once the moment is captured.
  Hint Camera layer.
- A payoff line the user would *want* in their Snap — "Bring this to the booth to redeem merch"
  (`Final-Copy`) — is content, even though it reads like a call to action. 2D UI.

Do not sort by whether something sounds like a CTA; sort by whether it belongs in the saved
image. When it is genuinely ambiguous, ask.

Other layers in this project — `1` Default (scripts/logic), `8` Capture layer, `16` Camera 3D —
are for advanced cases; do not put screen images on them without being told to.

Verify a layer with the object's `layers` mask in `.virtual-scene.json`, not by eye.

#### Parent and layer are set independently — a hint needs both

They answer different questions and neither substitutes for the other:

```
World          (parent)  → which camera facing shows it
layers = 2     (mask)    → which camera renders it → whether it survives capture
```

A world-only hint is parented under **`World`** *and* has its layer set to **`2`**. Parenting
alone leaves it in captures; setting the layer alone shows it on both facings. Confirmed by the
project's own `Swap Camera Animation`, which does exactly this.

Note that `World` / `Selfie` sit under the `2D  UI` camera but their children can carry a
different layer mask — the ScreenTransform hierarchy positions the element, the layer mask picks
the camera. The camera-facing behaviour comes from `World & Selfie.js`
(`Assets/Scripts/Scripts Starter Pack/`), whose `worldSide` / `selfieSide` inputs are already
wired to the `World` and `Selfie` group objects. Anything parented under them inherits the
enable/disable on flip for free — **do not add individual elements to those arrays**.

#### 2. What render order?

`Image.renderOrder` decides who draws on top **within a layer** — it has no effect across layers,
since the camera render order already settles that. Higher = drawn later = on top.

- **Leave it at `0` unless something on the same layer actually overlaps.** A non-zero value has
  to be justified by a specific element it must sit above; inventing one is noise that later
  reads as a deliberate constraint.
- **The Hint Camera layer is composited above everything**, so elements there stay at `0` — there
  is nothing above them to fight for.
- **The logo is always `99`** — the one standing exception, so branding stays above the 2D UI
  content it shares a layer with.
- When elements on one layer genuinely overlap, ask the user for the stacking order rather than
  guessing; they will always say who sits above whom.

### The Fader — how visibility works in this project

`Fader.js` v1.2.2 lives in `Assets/Scripts/Core.lspkg/Components/Fader/Fader.js`. `Core.lspkg` is
a **packed** package, so it is not browsable on disk — read the source at
`Cache/TypeScript/Src/Assets/Scripts/Core.lspkg/Components/Fader/Fader.js` (read-only; never edit
anything in `Cache/`).

A Fader script component is added to **every** UI element. It is the standard mechanism here, not
an occasional effect. Understand it before touching visibility, animation, or initial state.

#### What it does

It animates an element in and out with independently configured **In** and **Out** settings, each
with its own mode, duration and easing:

| Mode | Animates |
|---|---|
| `fade` | material alpha (`baseColor` by default), optionally recursive to children |
| `scale` | transform scale, local or world |
| `slide` | ScreenTransform anchors, toward a target rect |
| `move` | position, local or world; `applyMoveAsOffset` treats it as a delta |

`initialState: "hidden"` calls `hide({time: 0})` during init — the element snaps to its out-state
immediately **while remaining enabled**. This is why frame-2 and frame-3 elements are invisible in
the preview despite `enabled: true`, and it is the correct way to author them.

`disableWhenHidden` (off by default) additionally disables the SceneObject once faded out. The
script warns if it is pointed at its own object, since that would prevent it ever being shown again.

#### Driving it at runtime

```js
global.faderManager.show(identifier, animOptions, onComplete);
global.faderManager.hide(identifier, animOptions, onComplete);
global.faderManager.toggle(identifier, animOptions, onComplete);
global.faderManager.setAlpha(identifier, alpha);
```

`identifier` is a **fader name, a tag, a SceneObject reference, or an array mixing them**.
`animOptions`: `time`, `delay`, `mode`, `cancel` (`"none"` default / `"active"` / `"all"`),
`onStart`, `onComplete`. A bare function in the second slot is shorthand for `onComplete`.

**The fader name defaults to the SceneObject's name.** That makes object naming part of the
runtime API — `global.faderManager.show("TD-Bank_Logo")` works only because the object carries
that exact name. One more reason the naming convention is not cosmetic.

**Prefer a SceneObject reference over the name string.** Pass an authored element through a
`// @input SceneObject` and hand *that* to `faderManager`, rather than hard-coding its name — a
rename in the Scene panel then costs nothing, while a string silently stops resolving. Name
strings and tags are for cases where there is no reference to hold: generated cells, whole rows,
elements addressed from a script that does not own them.

When an identifier does not resolve, the manager warns rather than throwing:

```
FaderManager - WARNING, Failed to resolve - identifier undefined
```

`identifier undefined` means the argument itself was `undefined` — a mistyped `script.<input>`
name, not a Fader/wiring problem. JavaScript returns `undefined` for a missing property without
complaining, so read the warning as "check the spelling of the thing you passed" before
inspecting the scene. A different word in place of `undefined` is the real lookup failure: a name
or tag no Fader registered.

Requires `global.easing`, provided by `Global Properties & Functions.js`.

#### Fading GPU particles

Particle systems fade through the same Fader, with one setting changed: set the fade **Parameter**
to `particles` instead of `baseColor` (both `inFadeMaterialParameter` and `outFadeMaterialParameter`).
`Fader.js` has a branch for it that writes the alpha into the particle material's lifetime
parameters — `alphaStart` / `alphaEnd` / `alphaMin*` / `alphaMax*` — because a particle material
has no `baseColor` to write to.

So a particle effect is never switched with `enabled`. Leave the object **enabled** with
`initialState: "hidden"` like any other element, and drive it with `faderManager.show()`. The
system keeps simulating while invisible, which is the price of the fade; it only matters for
effects that idle for a long time before appearing. Do **not** reach for `disableWhenHidden` to
avoid that cost — combined with `initialState: "hidden"` it disables the object during init and
the effect can never be shown again.

#### Why one material per Image matters here

`fade` mode writes alpha into the material's `baseColor`. Two Images sharing a material would
fade together. This project sets `makeMaterialsUnique: false` — which is only safe *because* every
Image already owns its material. Breaking the one-material-per-image rule breaks fading.

### Materials

The `ScreenImageObjectPreset` creates a **fresh material per image**, and dumps **three things**
into the root of `Assets/`:

| Litter | What to do |
|---|---|
| `Image.mat` | Rename to the texture name, `moveAsset` → `Materials & Shaders/Materials` |
| `flat.graphShader` | **First image only** — the preset reuses the existing shader afterwards. `moveAsset` → `Materials & Shaders`; the material's pass depends on it, so move, never delete |
| `Image.png` | Placeholder texture, unused once the real texture is assigned — `deleteAsset` (a fresh one is dropped on *every* creation) |

Find the litter by id without guessing: `assetByPath(path: "Image.png")`, `assetByPath(path: "Image.mat")`.

Keep one material per image — never point two Images at the same material, since the texture
lives on the material and the second assignment would silently retexture the first.

### `Assets/` root must stay empty of loose files

**The root of `Assets/` holds folders and `Scene.scene` — nothing else.** Every asset created
during a task gets moved into its folder or deleted **before the task is called done**, in the
same turn. This is not a periodic cleanup; leaving litter for later is the failure mode, because
each new screen image adds another three files and the project stops being navigable.

Checklist after creating anything from a preset:

```
ls Assets  →  Audio  Components  Materials & Shaders  Misc  Render Targets
              Scene.scene  Scripts  Textures
```

Anything else in that listing is unfinished work.

### Naming

**A screen image and its material both take the name of their texture** — `TD-Bank_Logo`, not
`Logo` or `Image`. Object, material, and texture stay in sync, so any one of them can be traced
to the other two by name alone. (The Smart Scaler plugin enforces this automatically; match it
by hand when working through MCP.)

| Topic | Convention | Learned on |
|---|---|---|
| 2D UI parent | `2D  UI` → `Full Frame Region - Global` → `Global` (default) / `Selfie` / `World` | 2026-08-06 |
| Object + material naming | Both named after the texture (`TD-Bank_Logo`) | 2026-08-06 |
| Material location | `Materials & Shaders/Materials` | 2026-08-06 |
| Screen image scale | `±texture_width / 720` on left/right — native pixel size, never eyeballed | 2026-08-06 |
| Layer choice | `2D UI` (mask 4) for captured content, `Hint Camera` (mask 2) for hints/CTAs | 2026-08-06 |
| Logo render order | Always `99` — above everything | 2026-08-06 |
| Design canvas | 720 × 1280 px; 2 anchor units = 720 px wide | 2026-08-06 |
| Units / scale defaults | Lens Studio: cm, right-handed, +X right, +Y up, −Z forward | baseline |

### R1 — Add a screen-space image from a storyboard

1. `VirtualScene(read)` → serializes to `project://.virtual-scene.json`. Parse it for the target
   parent's `id` and for existing conventions. Cheaper than repeated GraphQL introspection.
   **`.virtual-scene.json` is a snapshot, not a live view** — it does not refresh when you mutate
   the scene or recompile a script. Re-run `VirtualScene(read)` before every inspection, or you
   will read stale values and conclude a change failed when it landed.
2. Find the texture: `asset-graphql { assetsByName(name: "...") { id name path type } }`.
   (`assets(...)` is **not** a valid root — use `allAssets`, `assetsByName`, `asset(id:)`,
   or `assetByPath(path:)`.)
3. `scene-graphql mutation { createSceneObjectFromPreset(presetName: "ScreenImageObjectPreset",
   name: "<Element>", parentId: "<Global id>") }` — creates ScreenTransform + Image in one call.
4. `VirtualScene(read)` again to pick up the new object's and material's ids.
5. Clean up + wire the material (see *Materials* above), texture path
   `passInfos.0.baseTex`, `valueType: REFERENCE`, value = texture asset id.
6. Set the rect on the **ScreenTransform component id** (not the SceneObject id):
   `setProperty(propertyPath: "anchor.leftBottom" | "anchor.rightTop", valueType: VEC2)`.
7. Capture the preview and compare against the storyboard.

### R2 — Sizing and positioning a screen image (THE method)

**Never measure pixels off the storyboard to derive a size.** The storyboard tells you *where*
an element goes; the **texture resolution** tells you *how big* it is. There is exactly one
correct scale and it is computable.

#### Horizontal — from the texture width

Assets for this project are authored on a **720 px-wide canvas**. Anchor space spans −1 … +1,
so **2 anchor units = 720 px** and an element's half-width in anchor units is simply:

```
value = texture_width_px / 720
anchor.left  = -value
anchor.right = +value
```

This renders the asset at its **native pixel size** — a 126 px logo occupies exactly 126 px of
the 720 px canvas. It is not a judgement call, so do not eyeball it and do not "adjust to taste".

This is the rule implemented by the user's own **Smart Scaler** plugin
(`~/Desktop/Smart-Scaler/MyPlugins/Smart Scaler/main.js`), which applies it from a right-click
in the Scene panel. When working through MCP, compute the same value by hand.

> Read the texture's pixel width straight from the PNG header rather than opening the file:
> `python3 -c "import struct;f=open(P,'rb').read(24);print(struct.unpack('>II',f[16:24]))"`

#### Vertical — pin the edge the element belongs to, drive the other

Do **not** compute a symmetric top/bottom pair. The Image renders with `stretchMode: Fit` and
`verticalAlignment: Center`, so the art is centred inside its rect at the aspect its width
already fixed. That means one anchor edge stays pinned to the screen edge and the *other* edge
moves the element:

| Element sits at the… | Pin | Drive |
|---|---|---|
| **top** of the screen | `anchor.top = 1` | lower `anchor.bottom` to move the element **down** |
| **bottom** of the screen | `anchor.bottom = -1` | raise `anchor.top` to move the element **up** |

The element ends up centred in the resulting rect, i.e. at `(top + bottom) / 2`.

*Worked example — TD-Bank_Logo, 126 × 113, top of screen:*
`left/right = ∓126/720 = ∓0.175`, `top = 1`, `bottom = 0.5`
→ rect centre `y = 0.75` → 12.5 % down from the top, matching the storyboard.

#### Pin to a side edge too, not just top/bottom

The pinning rule is not vertical-only. An element that belongs to the **left or right edge** gets
that anchor set to `∓1` and is sized with the opposite one:

```
anchor.right = 1
anchor.left  = 1 - 2 × value      # right-edge element
```

Placing such an element by its measured centre instead leaves a sliver of background between it
and the edge — visible, and it changes width with the aspect ratio.

*Worked example — Replay-btn, 110 px, right edge:* `right = 1`, `left = 1 − 2(0.1528) = 0.6944`.

#### Off-centre elements

`value` is a **half-width, not a position**. For anything not horizontally centred, read the
centre off the storyboard and place the pair around it:

```
anchor.left  = centre_x - value
anchor.right = centre_x + value
```

The same applies vertically when neither screen edge is the natural anchor. `Fit` plus
`horizontalAlignment: Center` / `verticalAlignment: Center` means the art always lands at the
rect's centre, so getting the centre right is the whole job.

*Worked example — Replay-btn, 110 × 121, right side of frame 3:*
`centre = (0.84, −0.314)`, `value = 110/720 = 0.1528`
→ `left/right = 0.6872 / 0.9928`, and vertically `bottom = −1`, `top = 2(−0.314) + 1 = 0.372`.

#### Full-bleed elements

A 720 px-wide asset yields `value = 1.0`, i.e. `left/right = ∓1.0` — the anchors sit exactly on
the screen edges. That is the formula working, not a mistake: 720 px *is* the full width.

For such an element, make the rect exactly the texture's size so it hugs its edge instead of
being centred in a taller box:

```
top = -1 + 2 × (texture_height / 1280)      # bottom-anchored, bottom = -1
```

*Worked example — Bottom-Gradient, 720 × 290:*
`left/right = ∓1.0`, `bottom = -1`, `top = -1 + 2(290/1280) = -0.5469`
→ rect is exactly 720 × 290 at the bottom edge, and `Fit` fills it precisely.

Keeping one edge pinned to the screen edge is what makes the layout survive different aspect
ratios — a top element stays glued to the top instead of drifting toward the centre.

### R2b — Elements that share a slot across storyboard frames

Different frames often reuse the same slot — e.g. `Rank-Your-Investments_Titile` (frame 1) and
`Final-Message` (frame 3) sit in exactly the same place. Handle them like this:

- **Give them identical anchors**, not separately measured ones. If the textures share a
  resolution the numbers are literally the same; even when they differ, `Fit` +
  `verticalAlignment: Center` centres each inside its rect, so a shared `top`/`bottom` pair
  keeps their centres aligned regardless of texture height.
- **Perfect overlap in the preview is the proof of alignment** — capture with both enabled once,
  confirm they sit on top of each other, then set the initial state.
- **Never duplicate the scene object to copy the placement.** Duplication risks sharing the
  material, and one material per image is a hard rule. Go through the preset and retype the
  anchors.
- Same `renderOrder` is fine for elements that are never on screen at the same time.

### Initial scene state = storyboard frame 1 — via the Fader, not `enabled`

The scene as authored must look like the **first** storyboard frame. But visibility in this
project is **not** driven by the `enabled` flag — it is driven by the **Fader** (see below).

**Leave every element you create `enabled: true`.** An element that should not appear in frame 1
gets a Fader with `initialState: "hidden"`, which drives it to its out-state at init while the
SceneObject stays enabled. Disabling the object instead would stop its Fader from ever running,
so it could never be shown again.

Fader configuration is the **user's** call — they set the modes and timings. Create the element,
place it, leave it enabled, and say which frame it belongs to.

### R7 — Tapping a screen element in the Preview

`InjectPreviewGesture` takes render-space `[0..1]` coordinates and explicitly warns against
estimating them off a screenshot (letterbox bars make that unreliable). Compute them from the
element's anchors instead — the conversion is exact:

```
x = (anchor_centre_x + 1) / 2          # anchor −1…+1  →  0…1, left to right
y = (1 - anchor_centre_y) / 2          # anchor +1…−1  →  0…1, top to bottom
```

For generated cells there is no authored anchor to read, so derive the centre from the same
layout inputs the generator used (`boardX`, spacings, the base's width/height). Getting a cell's
tap to land is then a check that the generator's maths and the tap maths agree — if the tap
misses, one of the two is wrong.

Drive a multi-step flow with the `gestures` array plus `delayMs`, sized to whatever the flow
waits on (a 1.5 s spin needs a delay comfortably above it), and capture once at the end.

### R4 — Installing an Asset Library package

```
SearchLensStudioAssetLibrary(keywordFilter: ["swap camera", "flip camera"], onlyMostRecent: true)
InstallLensStudioPackage(packageUri: "<uri from the result>", assetName: "<name>")
```

A package installs itself into **`Assets/Components/<Name>.lspkg/`**, self-contained with its own
`Textures/`, `Materials/`, `Shaders/` and prefab. Shared dependencies go to **`Packages/`** at the
project root (e.g. `Visual Demonstration.lsc`). Neither violates the clean-root rule; **do not
move or reorganise either** — the package manifest tracks those paths.

Note the asset path reported *during* installation is project-relative and can read as
`Packages/…`; the real on-disk location only settles after the project is saved. Check with
`git status` or `ls` after a save rather than trusting the install-time path.

**Snapshot the scene object list before installing.** Some packages instantiate themselves into
the scene, and `instantiatePrefab`'s `instantiatedEntities: []` in the response **cannot be
trusted** — an install that reported an empty list still dropped a copy under `Capture Camera`.
Diff object counts before and after; if a stray copy appeared, delete it and keep the one you
placed deliberately.

Read the package's returned `description` / README — it usually names the prefab and where it
belongs (e.g. *"drag `… __PUT_IN_ORTHO_CAM` under the Orthographic Camera"*).

**A prefab arrives on its own layer** (e.g. mask `1048576`), which none of this project's cameras
render. Set the layer explicitly, **on every object in the subtree** — `setLayers` does *not*
propagate to children.

**Check the package's own script inputs before wiring anything around it.** The Hint packages
carry a `VisualDemonstration` script that already implements `showType`
(On Front / On Back / On Both), `hideOnCapture`, `showOnce`, `screenDuration` and
`repeatCount`. Duplicating that logic externally fights the asset instead of configuring it.

### R5 — Asset Library assets are NOT scaled by the 720 rule

The `texture_width / 720` formula applies to **flat screen images authored for this project**.
An Asset Library asset — anything animated, or shipped with its own prefab and materials — comes
with a scale and anchor set that its animation depends on. **Use it as it arrives; do not
recompute its anchors.** Position it, but leave its size alone.

Elements you author *around* such an asset (a caption under an animated hint) are still your own
screen images and do follow the 720 rule.

### R6 — Generating repeated screen elements from a base object

Large repeating layouts (a ranking board, a grid of slots) are **not** built by hand. Author one
correctly-scaled screen image in the scene, wire it as a `baseObject` input, and generate the rest
in code.

```js
// copySceneObject is a method on SceneObject — NOT on `scene`/`global.scene`.
// It shallow-copies (components yes, children no) and parents the copy to the
// object it is called on.
const parent = base.getParent();
const cell = parent.copySceneObject(base);
cell.name = base.name + "_" + column;
```

Read sizes off the base rather than hard-coding them, so re-scaling the base re-scales the board:

```js
const anchors = base.getComponent("Component.ScreenTransform").anchors;
const width  = anchors.right - anchors.left;
const height = anchors.top   - anchors.bottom;
```

**Make the base itself the first cell** instead of copying it and hiding the original — that keeps
whatever Fader and material wiring the user set up on it, rather than duplicating and orphaning it.

Copies inherit the base's Fader, and each Fader clones its own material at init, so the
one-material-per-image rule holds automatically — do **not** create materials per generated cell.

**Generated cells cannot be addressed by name.** A copied object's ScriptComponents run their
lifecycle *inline at copy time*, so the Fader registers itself while the copy still carries the
base's name — renaming the object afterwards does not change the registered fader name. Every
generated cell therefore answers to the base's fader name.

Two ways to drive them:

- **`faderManager` accepts SceneObject references.** Keep the generated objects in a structure and
  expose it (`script.rows`), then pass the object itself.
- **A fader tag set on the base** is inherited by every copy — the way to move a whole row or board
  at once.

Still set readable `name`s on copies; they matter in the Scene panel and when debugging, just not
as a runtime handle.

Expose every layout number as an input (`// @ui` sliders for position, count, spacing) — a
designer tunes the board from the Inspector, never from the code.

**Setting a texture at runtime uses the Lens API, not the Editor API:**

```js
image.mainMaterial.mainPass.baseTex = texture;   // runtime  (Lens API)
// setProperty(..., "passInfos.0.baseTex", ...)  // authoring (Editor API) — see P1
```

Same property, two APIs, two spellings. Which one is correct depends on *when* you are writing it.

**Making a generated cell tappable:**

```js
sceneObject.createComponent("Component.InteractionComponent");
```

On a screen image that is the whole job — the component picks up the ScreenTransform's area
automatically. Do **not** call `addMeshVisual`; that is for mesh-based hit testing in 3D.

### R3 — Capture the preview

`PreviewPanelTool(screenshot)` fails on this install ("requires the tryScreenshot API,
Lens Studio 5.23+"). Use instead:

```
CapturePanelScreenshotTool(pluginId: "Snap.Plugin.Gui.PreviewPanel")
```

It returns the rendered 720×1280 Lens output with no editor chrome — directly comparable to a
storyboard frame. `CaptureRuntimeViewTool` is for 3D/world objects, not screen-space UI.

**A capture taken immediately after a mutation can miss elements** — the preview recompiles and
the frame is grabbed mid-rebuild. An element that vanished from a capture but reads as
`enabled: true` with correct anchors in `.virtual-scene.json` is almost always this. Re-capture
before investigating; the scene graph is the source of truth, the capture is a snapshot of a
live process.

## 5. Pitfalls & Corrections

*(The most valuable section. Each entry: what I did wrong → why it was wrong → the rule.)*

**P1 — `mainPass` is Lens API, not Editor API.** I set a material texture with
`mainPass.baseTex` and got `'mainPass' not found`. `mainPass` only exists at *runtime*
(Lens API). Through `asset-graphql` / `ExecuteEditorCode` the pass is an indexed array.
**Rule:** in the Editor API use `passInfos.0.<property>` — `passInfos.0.baseTex`,
`passInfos.0.baseColor`. Never `mainPass.*` in editor-side code.

**P2 — Presets leave litter at the project root.** `ScreenImageObjectPreset` wrote a material
named `Image` straight into `Assets/`, next to `Scene.scene`. Left alone, every new image adds
another `Image`, `Image 2`, `Image 3` at the root and the project becomes unnavigable.
**Rule:** rename and `moveAsset` any preset-created asset into its proper folder in the same
turn you create it — never as a later cleanup pass.

**P4 — I measured the storyboard to get the logo's size, and got it 15 % too small.**
I derived `±0.1495` by measuring pixels in the storyboard mockup; the correct value was
`±0.175 = 126/720`. The storyboard is a *layout* reference drawn at an arbitrary scale — its
pixel dimensions are not the spec. **Rule:** size comes from the texture resolution (R2), position
comes from the storyboard. Never derive a scale by measuring an image.

**P5 — I set top and bottom symmetrically around a computed centre.** That un-pins the element
from the screen edge, so it drifts on other aspect ratios. **Rule:** pin the edge the element
belongs to (`top = 1` for top elements, `bottom = -1` for bottom elements) and move it with the
opposite edge only.

**P7 — I put a selfie-only element under `Global` because I treated `Global` as the default.**
The title appears in the storyboard's selfie frames but not in its world frame, so `Selfie` was
the answer and it was sitting in the storyboard the whole time. **Rule:** `Global` is not a
fallback for "unspecified". Diff the world-view frame against the selfie frames and let that
decide — every element belongs to exactly one of the three, and the storyboard always says which.

**P9 — I set `renderOrder = 30` on two Hint Camera elements for no reason.** I copied the number
off the Asset Library prefab's Image, as if matching it meant something. Nothing on that layer
overlapped them, and the layer already composites on top. **Rule:** `renderOrder` is only ever
set to solve an actual overlap you can name. Copying a value from a neighbouring object is not a
reason. Default `0`.

**P11 — `QueryRuntimeSceneTool`'s `componentTypes` summary is not exhaustive.** Freshly created
`InteractionComponent`s did not appear in it, and I nearly concluded the code was broken when it
was working. **Rule:** when runtime introspection says a component is missing, confirm from inside
the Lens before changing anything —

```js
const c = obj.createComponent("Component.InteractionComponent");
print(c && c.getTypeName());   // → "Component.InteractionComponent"
```

Delete the temporary `print` in the same turn you added it. A tool's summary view is evidence,
not proof; the runtime's own answer is proof.

**P10 — I guessed a Lens API signature and shipped `global.scene.copySceneObject(...)`.**
It threw `TypeError: not a function`; the method belongs to `SceneObject`, not the scene.
**Rule:** verify every Lens API call against `Support/StudioLib.d.ts` before writing it —
`grep -n "<methodName>" Support/StudioLib.d.ts` also shows which class owns it and what the
doc comment promises (here: *shallow* copy, auto-parented to the receiver). `Support/editor.d.ts`
is the *other* API and will happily mislead you. Then confirm with
`RecompileTypeScriptTool` + `RunAndCollectLogsTool(mode: "refresh")` — a silent preview is not
proof, but an empty `errors` array plus the expected capture is.

**P8 — I invented UUIDs twice instead of looking them up.** I passed
`e3f8d0e6-0000-0000-…` and `e1a72f1f-0000-0000-…` as parent and component ids; both failed with
"not found". Harmless here because the API rejected them, but the same reflex applied to a
*valid* id would mutate the wrong object silently. **Rule:** every id in a mutation is copied
from a `.virtual-scene.json` read or a GraphQL query in this same session. If you do not have it
in front of you, fetch it — never pattern-match a plausible-looking UUID.

**P6 — Before deleting a preset leftover, prove it is unreferenced.** Two `flat.graphShader`
assets existed with the same name; only one was wired to the logo material. Names and folders do
not tell you which. **Rule:** resolve the actual reference before deleting anything —

```ts
// ExecuteEditorCode — what does this material's pass actually point at?
const mat: any = model.project.assetManager.assets.find(a => String(a.id) === MAT_ID);
for (const e of mat.passInfos[0].getDirectlyReferencedEntities()) print(String(e.id));
// → [ baseTex id, shader id ]
```

`getDirectlyReferencedEntities()` is the reliable way; the shader is **not** exposed as a plain
property on `PassInfo` (its own keys are only defines/blend/depth state), and the `.mat` file on
disk reads `PassesInfo: []` until the project is saved, so neither the property list nor the file
can answer the question. Moving an asset preserves its id and breaks nothing; deleting is what
needs the proof.

**P3 — `setProperty` on ScreenTransform takes the component id.** Anchor writes go to the
**ScreenTransform component's** id, not the SceneObject's id. Read both out of
`.virtual-scene.json` (`components[].id`) before mutating.
